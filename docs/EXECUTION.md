# 执行方案：从空目录到可安装客户端

在**升级版根目录**构建和运行测试。各阶段的实际结果见 [验收记录](VERIFICATION.md)，架构与旧版功能对应见 [技术设计](DESIGN.md) 和 [迁移方案](MIGRATION.md)。

## 1. 实施顺序与完成条件

角色表示职责，不预设团队人数。先交付可试装的窄链路，再移植全量业务；不要等十类中间件都改完才发现 Electron 找不到 Go。

| 阶段 / 前置 | 主要工作（建议牵头角色） | 交付件与放行条件 |
|---|---|---|
| **P0 旧版基线** / 无 | 迁移负责人冻结经用户确认的源码、未提交改动、配置与清单快照；按远端 OS/CPU 列支持/拒绝/未证实组合。选一台可还原的授权测试机；开发初期只用模拟器 | 基线记录、十类应用映射、脱敏脚本输出、微型资源包、合成旧库；真实主机/生产数据库不入库。待确认项写明影响，绝不通过还原旧工作树来“清理基线” |
| **P1 可安装骨架** / P0 | 桌面负责人建 npm workspace 与锁、Go 单模块、preload 和 IPC Schema。实现 `hello`、Go 启停/超时、错误窗口、最小 Windows x64 打包；版本与工具链固定到锁文件/CI | 在无 Go/Node/.NET 开发工具的干净 Windows 账户安装 `.exe`，断网可开 UI、握手成功、显示壳/Go/协议版本；路径带空格/中文可启动，退出无孤儿进程；删掉测试副本中的 Go 时能清楚报错 |
| **P2 主机与只读检测** / P1 | Go 负责人实现主机 CRUD/分组、指纹与凭据适配、OS/CPU 检测、SQLite、状态脚本解析。React 做主机编辑、测试连接、单应用检测与日志 | 从**安装版**选合成/授权主机到状态可见；未安装 ≠ 检测失败；指纹变化会阻止连接。没有 SFTP 时保留可用的只读 SSH 能力。此阶段不触发安装或卸载 |
| **P3 第一条安装闭环** / P2 | 实现资源预检、签名/哈希验证、脚本隔离上传、持久任务、取消/断线、复查与结果判定。优先以 Ubuntu 24.04 + 一个有完整离线包的组件（如 Mosquitto）为验收对象 | 先审核卸载影响范围/保留数据策略，不满足则阻止执行；在可恢复快照上完成导入 → 安装 → 检测 → 卸载 → 数据与残留复查，同时验证预置数据和非目标服务。错架构、缺依赖或校验失败时上传次数为 0；不要求工作站联网 |
| **P4 功能对齐** / P3 | 分组移植批处理与剩余应用、配置/脚本编辑、自定义部署、终端/SFTP、历史/日志/设置、更新检查。每一组独立对照迁移矩阵；为并发检测、日志流和 PTY 做专项测试 | 每项都有旧证据、Go/React 用例、适用平台与结果；检查 JDK 单机限制、Traefik 双配置、同主机串行卸载等例外。未测的组合保留为未测，不因同一应用在另一系统成功而放行 |
| **P5 数据迁移与多平台试装** / P2 后可备夹具，正式门禁依赖 P4 | 数据负责人用副本演练导入、凭据补录与回退。发布负责人搭建 Windows、macOS、Linux 原生构建任务，分别嵌入同目标 Go，验证系统依赖、密钥库和卸载/升级行为 | 合成旧库六表核对、重复导入无新增重复项、导入失败仍能正常启动旧版；每个拟发布 OS/CPU 至少有一份安装版试装记录。缺 runner 或签名身份标记受阻，不能写成“支持已验证” |
| **P6 试点和发布** / P5 | 发布负责人核对支持矩阵、基础包/离线包两份发布清单、哈希、软件许可、版本说明与签名。先小范围试点，再由负责人批准分发 | 有安装/升级/卸载记录、试点问题和回退演练；安装程序不删除用户数据，试点能在旧版继续工作。构建、签名、对外发布是三项独立动作；CI 测试默认不发布 |

## 2. P1 如何创建可维护的工程

1. 在升级版建立根 `package.json`、一个根 `package-lock.json`，workspace 包括 `apps/desktop` 和 `packages/protocol`；建立 `backend/go.mod`/`go.sum`，Go 构建入口为 `backend/cmd/installer-core/`。固定开发 Node/Go 和受支持的 Electron 版本，区分开发 Node 与 Electron 内置 Node；先在所需 CPU 上验证 SQLite 驱动。
2. 先写 IPC 成功、业务失败、乱序/断连三类夹具；实现 Go `hello` 与 Electron 超时/崩溃处理；再写 preload 和极小状态页面。开发环境可有仅回环的 Vite 服务，生产包不得引用开发服务器或远程 CDN。
3. 定义开发、测试、打包共用的 Go 路径解析器。打包前先构建指定 OS/CPU 的 Go，再构建 renderer/main/preload，最后交给 electron-builder。产物写专用输出目录，用户数据与资源缓存不随应用更新覆盖。
4. CI 第一条路径用 Windows x64：安装依赖 → 静态检查/单元 → 共享协议夹具 → 打包（禁止发布）→ 安装版冒烟 → 留存工件与测试记录。后续扩展 runner，生产签名凭据不出现在普通测试、PR 或日志中。

## 3. 本地构建与测试命令

从升级版根目录执行。使用 Node.js 22.22 和 Go 1.26.11；首次安装需要下载 npm、Electron 和 Go 依赖。本机操作和部署验收结果见 [验收记录](VERIFICATION.md)。

按照锁文件安装 JS 开发依赖与 Electron 运行时。

```bash
npm ci
```

开发模式会编译本机 Go 和生产界面，然后打开 Electron。启动和退出使用与打包版相同的进程管理逻辑。Vite 的独立界面预览入口是 `npm run preview:ui`。

```bash
npm run dev
```

检查 TypeScript、静态规则及 Go：

```bash
npm run typecheck
```

```bash
npm run lint
```

```bash
go -C backend vet ./...
```

运行协议夹具、前端组件测试和 Go 单测：

```bash
npm run test:contract
```

```bash
npm run test:ui
```

```bash
go -C backend test ./...
```

按用例名运行安装判定或首次指纹确认测试。

```bash
go -C backend test ./internal/operations -run '^TestInstallDecision$' -count=1
```

```bash
npm run test:ui -- -t '首次添加必须明确核对指纹'
```

构建开发验证所用的本机 Go、界面、桌面主进程和 preload。

```bash
npm run build:core
```

```bash
npm run build
```

```bash
npm run test:core:stdio
```

```bash
npm run test:e2e:local
```

生成当前系统和 CPU 的安装包。入口会重建 Go 和生产界面，并将产物与 `BUILD.json` 写入 `artifacts/<platform>-<arch>/`。

```bash
npm run package:local
```

在同一操作系统生成另一种 CPU 架构的产物时使用 `--arch`。macOS DMG 在 macOS 构建，Linux DEB 和 AppImage 在 Linux 构建。测试不同 CPU 架构请使用对应的机器或运行器。

```bash
npm run package:local -- --arch arm64
```

`test:e2e:packaged` 默认运行打包输出目录中的桌面程序。验证已安装的副本时，通过 `RELAYDOCK_SMOKE_EXECUTABLE` 指定其可执行文件；该测试总是创建临时数据目录。Linux 无桌面显示服务时通过 `xvfb-run -a` 执行。

```bash
npm run test:e2e:packaged
```

## 4. 测试策略与放行证据

| 门禁 | 输入与方法 | 最低通过条件 |
|---|---|---|
| G1 协议/决策 | 同一组 Go/TS 正反例、旧脚本文本与 JSON 行、异常退出/状态复查组合 | 两端解码一致，未知版本明确失败；检测到未安装不算检查失败；警告能到达 UI，旧终态不被迟到进度覆盖 |
| G2 安全/副作用 | 模拟 SSH/SFTP、首次/变化指纹、伪造来源的业务请求、重复开始与取消、丢失 Go 进程 | 来源/授权无效不调用底层；重复请求最多建立一个写任务；失联后不自动重发；用户可见中断与复查提示 |
| G3 资源/远端 | 错架构/缺索引/哈希错误、显式在线与离线缺件两条互斥路径；授权 VM 上预置数据标记和非目标服务，执行安装及卸载 | 离线不匹配必须在上传前失败且不联网；已开放的在线组合需显式确认。逐组件核对允许变更清单、保留数据、非目标包/服务不变；复查不可用且无可信证据时不算卸载完成 |
| G4 数据 | 含 101 条以上任务的临时旧库、未合并 WAL、缺列、旧令牌、坏密钥路径；两份相同主键但 IP 改变的快照；在提交前和提交后立即模拟崩溃 | 事务内先核对数量、行差异、外键和凭据引用再提交；提交前失败可回滚，提交后恢复不删已引用凭据。源删/双向编辑需人工处理，地址改变不能静默连旧主机；新库、日志、导出不含敏感哨兵 |
| G5 桌面体验 | 仅键盘完成主机编辑/安装确认；终端调整大小与中断；连续日志、长列表、切换主机与主题 | 焦点可见并恢复；终端不截断/错序，SFTP 被禁不破坏终端；后台任务和历史完整，日志加载不冻结操作 |
| G6 发布 | 每种发布组合的干净机器/VM，无开发工具，断网启动；已装版升级、卸载后重装 | 核对 Electron/Go 架构与签名，握手可用；不依赖 PATH、写安装目录或残留 Go；保留用户库。记录未具备的 runner、证书与实测范围 |

**性能如何衡量：** 用同一组样本（建议 100 台合成主机、5 万行历史、模拟每秒 1,000 行日志持续 60 秒），区分开发版和发布版。记录三次冷启动到窗口可交互/Go 就绪时间、空闲及压力下**整棵进程树**的内存、基础包与资源包各自大小、终端输入延迟和最终事件数；日志不无限堆积、终态不丢是硬门槛。P1 存基线，P4/P5 复测；具体性能阈值以基线和试点目标确认，本文没有实测数字。

## 5. 发布矩阵与验收模板

下表是**目标组合而非支持声明**。每个 OS/CPU 分别记录最低系统版本；远端 CentOS 7 兼容性不等于 Electron 客户端支持 CentOS 7。新架构可先只发已试装的组合，不用模拟运行替代最终目标机验收。

| 客户端 | Go 目标 | 计划产物 | 必查项 |
|---|---|---|---|
| Windows x64；ARM64 单独变体 | `windows/amd64`；`windows/arm64` | 各自的 NSIS `.exe` | 优先交付 x64；检查发布者签名（正式版）、凭据库、带中文的用户路径和卸载保留数据 |
| macOS Apple Silicon；Intel 单独变体 | `darwin/arm64`；`darwin/amd64` | 各自的 `.dmg` | 在 macOS 构建；先签 Go、再签应用，正式分发用 Developer ID、Hardened Runtime、公证并 staple；在干净机器验证 Gatekeeper 和 Keychain |
| Linux x64；ARM64 单独变体 | `linux/amd64`；`linux/arm64` | Ubuntu/Debian `.deb` 优先；经适配再发 `.rpm` 或 AppImage | 记录发行版/系统库最低版本、可执行位、Secret Service 有/无两种行为；AppImage 是便携包而非系统安装向导 |

每份记录填写：客户端版本/构建号、OS/CPU、Go/协议版本、安装包文件名与 SHA-256、资源清单版本、远端组合或“未联网”、操作、预期/实得、日志证据、结论（通过/失败/受阻/未测）、回退结果。签名、公证、上传制品需在获准环境执行；缺条件时保留本地未签名测试产物并明确标识，不对外当正式版分发。

## 6. 工作台验收入口

按 [验收记录](VERIFICATION.md) 选择匹配工作站的安装包。启动后检查底栏本地核心，在「设置 → 旧版数据」用副本预览和导入，在「离线资源」导入单个审核目录。验证远端时，从一台可还原的测试主机开始，先确认 SSH 指纹并比对只读检测，再按对应组件的验证范围执行写操作。
